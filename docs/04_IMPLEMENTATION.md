# 04. Codex 실행 순서와 개발 계획

문서 버전: 1.0 | 시작 상태: 애플리케이션 미구현

## 1. 문서 적용 방법

이 패키지의 `AGENTS.md`, `docs/`, `.env.example`, `tools/kis-bridge/.env.example`을 프로젝트 루트에 둔다. 기존 AGENTS.md나 문서가 있다면 먼저 차이를 확인하고 병합한다. 사용자 문서를 통째로 덮어쓰지 않는다.

**이 패키지에는 실행 가능한 Next.js 앱이 아직 없다.** 아래 npm 명령은 P0에서 package.json과 실제 script를 만든 이후에 실행한다. 문서만 복사하고 npm run dev가 된다고 안내하지 않는다.

Codex는 작업 시작 시 AGENTS.md 지침을 읽는 구조를 제공한다. 다만 상세 docs는 작업 지침과 프롬프트에서 읽도록 명시한다. [S21]

## 2. 첫 번째 Codex 프롬프트

다음 내용을 그대로 전달한다.

```text
AGENTS.md와 docs/의 개발 문서를 읽고 현재 저장소를 먼저 확인해줘.

이번 작업은 docs/04_IMPLEMENTATION.md의 P0와 P1 중 첫 수직 기능까지만 진행해줘.
외부 API 키, Supabase, 한투 계좌가 없어도 실행되는 상태여야 해.

먼저 구현할 범위와 수정할 파일을 짧게 설명한 뒤 코드를 작성해줘.
Next.js App Router, React, TypeScript strict, npm을 사용해줘.
첫 수직 기능은 홈 검색에서 예시 종목 상세로 이동해 합성 현재가, 캔들,
호가, 최근 체결이 같은 데이터 흐름에서 움직이는 화면이야.
시세가 합성이라는 표시와 일시정지 기능도 함께 구현해줘.

연동 완료나 성능 수치를 만들어내지 말고, 실제로 실행한 typecheck, lint,
테스트, build 결과와 미실행 항목을 구분해서 보고해줘.
docs/05_QUALITY_AND_PROGRESS.md에 진행 상태를 갱신해줘.
Git 변경 작업, 원격 DB 변경, 배포는 하지 마.
```

처음부터 `전체 기능 한 번에 완성`을 요청하지 않는다. 기능이 많을수록 문서만 읽고 거대한 빈 구조를 만들기 쉬우므로 동작하는 작은 흐름부터 완성한다.

## 3. P0 | 저장소 확인과 실행 기반

### 작업
- 기존 코드/설정/사용자 변경사항 확인. 빈 저장소인지 기존 앱인지 기록.
- 루트 문서가 이미 있는 비어 있지 않은 폴더에서 scaffolder가 실패할 수 있으므로 문서를 삭제하지 말고 안전한 임시 생성 후 병합 또는 수동 설정.
- Next.js, React, TypeScript, npm, ESLint, Vitest, 최소 UI를 구성.
- 공식 문서와 peer dependency로 호환 버전 및 Node LTS를 선정하고 실제 버전을 기록.
- 앱의 단일 lockfile, tsconfig strict, 경로 alias, 서버/클라이언트 환경 검증 구성.
- secrets/실제 데이터/테스트 산출물 ignore 규칙 설정.
- `APP_ENV`, 세 가지 데이터/저장 모드의 검증 및 기본 synthetic/fixture/local 구성.
- 기본 layout, 데이터 모드 배지, 오류 경계, 로딩 화면 구현.
- smoke test를 만들고 명령을 실행.

### 완료 조건
키 없이 설치/개발/타입 검사/린트/유닛 테스트/빌드가 가능하다. 아직 만들지 않은 script를 성공하는 빈 script로 위장하지 않는다. 지원 버전, 실행 명령, 저장소 상태가 진행 문서에 기록되어 있다.

## 4. P1 | 시장 화면의 첫 수직 기능

### P1-A: 종목 하나로 끝까지
- MarketProvider 계약과 SyntheticMarketProvider 구현.
- 자체 합성 seed와 상태 엔진에서 quote/trade/orderbook/history 생성.
- 홈 검색 → 종목 상세 → 현재가/캔들/호가/체결 화면 연결.
- 시간순 집계, cleanup, pause/resume/reset 구현.
- 출처 배지, 연결 상태, 값 형식, 차트 크기 변화 대응.
- 네트워크/API 키 없이 동작하는 E2E 1개 작성.

### P1-B: 범위 확장
- 지원 종목 5~10개, 관심종목용 스트림, URL 기간/탭 상태.
- 데스크톱 2열과 모바일 세로 레이아웃.
- 1배/2배/4배, 숨긴 탭의 가상 시계 일시정지.
- 로딩/빈 목록/잘못된 종목/초기화 상태.

### 완료 조건
호가와 현재가/차트가 서로 모순되지 않고, 초기화 후 이전 타이머와 값이 남지 않는다. 한투 실제 데이터가 1바이트도 없어도 시세 화면을 체험할 수 있다. P1-A 완료 전 P1-B를 무리하게 넓히지 않는다.

## 5. P2 | DART 재무와 공시

### P2-A: 파서와 예시 계약
- company/instrument 구분, 보고서 원천 모델, normalized DTO 정의.
- 예시 fixture로 큰 금액, 빈 값, 연결/별도, IS/CIS 단일 분기, 누적 CF, BS 시점 테스트.
- 연간/분기 재무 표와 요약 차트, 원문/출처 표시 UI.
- 공시 목록과 원문 링크 UI.

### P2-B: 실제 수집
- DART 키를 로컬 환경파일로 설정하는 절차 작성.
- corpCode ZIP과 회사 개황으로 지원 목록 검증.
- `data:sync` 도구와 dry-run, 요청 예산, timeout, 실패 재개 기능 구현.
- 먼저 회사 하나의 사업보고서와 분기 보고서를 수집.
- 원문과 대조한 금액, 기간, CFS/OFS, 접수번호를 확인 기록에 남김.
- 검증된 원천으로 공개 DTO 생성.

2026-09-30 구현 상태: 로컬 수집/재개/검토 양식/DTO 내보내기 도구 코드를 작성했다. 도구 실행, 키 설정, 실제 원천 수집과 대조는 미실행이다. 사용자 지시로 P2-A 검증을 보류한 채 다음 기능으로 수집 도구만 개발했으며, 두 단계의 완료 조건을 통과한 것으로 보지 않는다. 키가 없다고 판명되면 실제 수집을 blocked로 기록하되 예시로 대체하지 않는다.

### 완료 조건
실제 원천이 있는 항목만 opendart로 표시한다. 키가 없으면 P2-A까지만 완료 처리하고 P2-B는 blocked로 둔다. 데이터 없음과 금액 0을 구분하고 분기 계산 테스트가 통과한다.

## 6. P3 | 관심종목, 비교, 리서치 노트

### 작업
- IndexedDB PersonalRepository와 저장 schemaVersion 구현.
- 관심종목 추가/삭제/정렬과 새로고침 유지.
- 최대 3개 기업의 같은 기간/기준 재무 비교.
- 노트 작성, 수정, 삭제, debounce autosave와 즉시 flush.
- 게스트 데이터의 JSON 내보내기/가져오기, 크기/스키마 검증, 초기화.
- 입력 실패/저장 실패/권한 없는 저장소/다중 탭 충돌 처리.
- 내보내기에 시세, API 키, 내부 캐시가 섞이지 않는지 검사.

### 완료 조건
로그인 없이 검색 → 기업 확인 → 비교 → 노트 작성이 이어진다. 저장 실패를 성공처럼 표시하지 않고 새로고침/다른 탭 상황에서 데이터가 조용히 사라지지 않는다.

2026-09-30 구현 상태: `/watchlist`, `/compare`, `/notes`와 개인 저장/충돌/백업 코드, 홈·상세 연결을 작성했다. 사용자 지시로 검증을 실행하지 않아 `implemented_unverified`다. P2 실제 수집/검증을 완료 처리하지 않고 fixture 기반 비교와 개인 기록으로 독립 진행했다. 기존 홈 URL 선택 목록의 별표 테스트는 브라우저 관심종목 저장 계약에 맞춰 후속 갱신이 필요하며 U01~U10과 F16의 검증 결과를 추정하지 않는다.

## 7. P4 | 공개 데이터 저장소와 배포 안전장치

### 작업

- 공개 miss가 외부 수집을 발생시키지 않는지 테스트.
- 데이터 source manifest와 공개 빌드 검사 도구 구현.

### 완료 조건
공개 배포 모드에서 시장 데이터 외부 호출이 없고, 실제 DART 데이터는 검토된 캐시에서만 제공된다. 한투 키를 일부러 추가하거나 kis-private으로 설정한 빌드는 실패한다. 원격 DB 작업은 사용자 요청 전까지 실행하지 않는다.

## 8. P5 | 개인 로컬 한투 실제 연동

### 준비 확인
계정의 API 사용 조건, 발급 키, 최신 한도와 공식 샘플 commit을 확인한다. 실제 장/체결이 없는 시간에는 수신 성공을 확인했다고 기록하지 않는다. API 키와 포털 비밀번호를 Codex 대화에 붙여 넣지 않는다.

### 작업
- 로컬 Node 중계와 Next 로컬 전용 HTTP 경계 구현.
- loopback bind, Host/Origin allowlist, 단기 티켓, read-only 경로 제한.
- REST 인증/현재가/과거 일봉 → WS 체결 → WS 호가 순서로 연동.
- 토큰 single-flight, 요청 큐, 구독 ref count, reconnect/backoff 구현.
- 다중 레코드 파서와 schema 변경 오류 처리.
- LocalBridgeMarketProvider를 합성 Provider와 같은 UI에 연결.
- REST 초기값이 새 WS 값을 덮어쓰지 않는지 검증.
- 재연결 gap, 정리되지 않은 구독, 다중 탭으로 인한 upstream 증가를 검사.

### 완료 조건
지원 종목 하나에서 실제 수신을 관찰하고 토큰 없이 비민감 검증 기록을 남긴다. 코드를 구현했지만 계정이나 장 상황 때문에 테스트하지 못했다면 `실제 수신 미검증`으로 남긴다. 이 경우 이력서에서 실제 검증 완료를 주장하지 않는다.

실제 시세 화면의 공개 스크린샷/동영상도 별도의 공개 이용 판단이 필요할 수 있으므로 포트폴리오 캡처는 합성 모드를 사용한다.

## 11. 단계별 완료의 구분

| 표시 | 뜻 |
|---|---|
| not_started | 아직 구현하지 않음 |
| in_progress | 코드 또는 검증 진행 중 |
| implemented_unverified | 코드 구현, 실제 외부 연동/브라우저 검증 일부 미실행 |
| blocked | 키/권한/외부 환경 등으로 진행 불가, 원인 기록 |
| done | 해당 단계의 구현과 정해진 검증 모두 완료 |

파일이 생겼다는 이유만으로 done으로 바꾸지 않는다. P5가 blocked여도 합성 포트폴리오 UI 작업은 진행할 수 있다. 최종 설명에서 실제 연동의 검증 상태를 숨기지 않는다.

| `test:perf` | P6 | 결정론적 합성 스트레스 시나리오 |
| `verify` | P6 | lint/typecheck/unit/build/public 검사 순차 실행 |

`dev:kis`는 Node launcher로 두 프로세스의 환경을 검증하고, 공유 비밀이 비어 있으면 cryptographic random 값으로 생성해 두 자식 프로세스 메모리에만 전달한다. 브라우저에는 단기 티켓만 준다. 종료 시 두 프로세스와 소켓을 함께 정리한다. 독립 `dev:bridge`에서는 공유 비밀이 없으면 실행을 거절한다.

환경변수 로딩은 Next.js의 기본 동작만 믿지 않는다. 별도 Node 도구도 명시적으로 해당 `.env.local`을 읽게 하고 Git에 포함하지 않는다. Windows에서도 동작하도록 셸 전용 export 문법에 의존하지 않는다.

## 13. 데이터 수집 도구의 안전한 실행 계약

아래는 작성된 CLI에 맞춘 명령이다. 이번 작업에서 실행하지 않았으며, 실행 검증은 사용자 요청 시 수행한다. 최초 수집은 종목 하나/연도 하나로 제한하고 실제 제출 보고서를 확인한다.

```bash
npm run data:sync -- --symbol 005930 --year 2025 --reports 11014,11011 --run samsung-2025-cfs --dry-run
```

- dry-run은 요청 계획과 최대 요청 수만 출력한다. 외부 API 호출/파일 갱신/원격 쓰기는 하지 않는다.
- 실제 수집 기본 출력은 Git에서 제외된 로컬 작업 경로다.
- `--resume --run ID`는 저장한 계획을 사용하며 완료한 요청은 원본 해시 확인 후 재사용한다. 요청 횟수와 예산도 유지하며 `--max-requests N`을 명시한 경우만 예산을 변경한다. 각 실행의 최대값은 1,000회다.
- `data:review --run ID --prepare`의 양식을 원문과 대조해 작성한 뒤 `--export`로 로컬 DTO를 생성한다. 상세 작성법은 문서 03의 5.4절에 있다.
- `data:publish`는 별도 명령이며 검토되지 않은 수집 결과를 자동 공개하지 않는다.
- 원격 데이터 변경 명령은 사용자가 요청했을 때만 실행한다.
